# Task 4 — System Design

The two most likely causes are an unindexed search query and too much repeated work. The endpoint may be using `%text%`, sorting, or joining large tables without useful indexes. At the same time, every user may be running the same expensive query against MySQL with no cache. I would first inspect the slow-query log and application timings, then run `EXPLAIN ANALYZE` for the exact slow query. I would check rows scanned, full table scans, temporary tables, sort work, connection count, and whether one search pattern causes most of the load.

Within 48 hours, I would add or correct one or two indexes based on that query plan, then introduce a short-lived cache for common search requests. A cache key would include the normalized search text, filters, sort, and page. A TTL of 30–60 seconds can remove repeated reads while keeping results reasonably fresh. I would also cap `limit`, require pagination, and add a safe query timeout. Index creation would use MySQL's online DDL support where available, tested first on production-like data, so the platform stays online.

Long term, I would move search to a dedicated search engine such as OpenSearch or Elasticsearch. MySQL would remain the source of truth. Artist changes would be published through an outbox and indexed asynchronously. The API would query the search index and use MySQL only for final authoritative data when needed. This gives fast text search, filters, ranking, and horizontal scaling without using the transactional database as a search engine. The accepted trade-off is eventual consistency: a new or updated artist may take a few seconds to appear in search. It also adds operational cost, another datastore to monitor, and a reindexing process.
